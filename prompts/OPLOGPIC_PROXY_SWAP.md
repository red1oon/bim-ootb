# OplogPic: proxy / swap idea (owner, 2026-10-12) — EXPLORATION, nothing built

**Idea (owner):** like the BIM viewer's batch mesh draw and bounding boxes, show a light representation of the picture and keep the real load out of the way: progressive, sharded / swapped, and do not load everything if it can be achieved visually.

**What we already have that fits (all in `poc/psd-oplog`):** the dirty-tile compositor (`perf/dirty.js`, 64x64 tiles, recomposites only the tiles an op touches with the unchanged canonical code); the content-addressed tile store (`tiles/tilestore.js`, 64x64 tiles; layers stored as tile blobs, exact); editor checkpoints (`editor/ckpt.js`, tile-style raw buffers, sha256-checked, IndexedDB); time-sliced work (blur brush queue). The hard rule that must stay: the canonical fold is full-resolution float32; a proxy is DISPLAY ONLY, never enters the log, the hashes, Verify, PSD export, or a checkpoint.

**Measured today (this host, system Chrome, `film/measure_ram.js` and `film/measure_layer_swap.js`, two runs identical):** the finished showcase file (5 layers) takes a renderer 508 MB against 213 MB for an empty editor, a 295 MB step. The editor's own arrays are 112 MB (layers 80, masks 4, picture blobs 12, compositor 16). Discarding the arrays of the three photo / caption layers drops the renderer to 440 MB (-68 MB); discarding all five layers drops it to 424 MB (-84 MB). So swapping layers out is real (about 16-22 MB freed per 16 MB layer) but it reaches only about 28 % of the 295 MB step; the other ~211 MB above the empty editor is NOT layers (candidates, unmeasured: the parsed save string and decoded picture blobs left on the heap, undo state, the 50 MB used / 115 MB total JS heap, canvas surfaces). A heap snapshot of the loaded page is the first thing to do.

**Tiers sketch (not built, numbers are arithmetic):** (1) resident = full-resolution tiles only for what is being edited, or tiles that are non-transparent (an empty Paint layer or a caption layer is mostly empty tiles: free); (2) proxy = a half-size 8-bit copy for display while zoomed out or dragging (a phone shows 1024 pixels in about 390 CSS pixels): 512x512 RGBA8 is 1 MB per layer instead of 16 MB; (3) swapped = untouched photo layers kept as their stored blob (4 MB raw, or compressed) and re-decoded to float32 tiles on first edit, evicted again when idle. Editing a layer materialises it; Verify, export and checkpoint materialise everything. Progressive: draw the proxy at once, refine tile by tile in idle slices (as the blur brush already does).

**Risks / constraints:** `stack.js` and the adjustment / mask code assume dense arrays, so every consumer must go through a tile accessor (large change, spec first); adjustments and masks need full resolution to be exact; the bit-equal dirty-compositor gates must keep passing; first edit after a swap costs a decode (a 4 MB blob is fast, but unmeasured on a phone); iOS Safari untested.

**Suggested spike (measured gates, no engine change):** (a) heap snapshot of the loaded showcase page and an accounting of the ~211 MB; (b) fix whatever of it is transient (release the parsed save string and blobs after load); (c) only then try tile-sparse storage for transparent tiles on the caption / paint layers and report the RSS drop; (d) a display-only half-size proxy for the Move preview and zoom-out, with a gate that the exported pixels and all hashes are unchanged. Not a promise: phone behaviour must be measured on a real phone.
