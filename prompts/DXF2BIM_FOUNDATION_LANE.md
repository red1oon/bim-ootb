**D9 result (built 2026-10-19).** Flag `opening.rect.door: true` in the standard-set config; a rectangle with no gap-end host also tries its two long-axis ends (the footprint lies in the gap between two wall pieces; nearer piece, tie lower handle); `applyDoorHeights` accepts a rect door and skips the hinge search. Hospital 85-deg wing: `no_dimension` 57 -> 0; 47 of the 57 get a schedule height; they now show as `no_host_cut` (the same informational cut gap arc doors carry), 10 have no height (6 `label_ambiguous`, 2 `label_unmatched`, 2 other): blocking 460 -> 470 (stated: honest gaps replaced vague ones, the total rose). HHS unchanged at 383; Duplex marks identical; suite 36 / 10 / 2 (pre-existing).

**Rule D10 (spec BEFORE code, then built; Hospital wing `QF:dim_point_missing` 65).** Measured: Level 1 east face, the reader's wall pieces end exactly on the drawn face (x = 85.4914 m) and need dimension points at their ends (101.26, 103.66, ...), but the writer measured the face against the model's bounding box (E = 85.5164 m, 25 mm outside the drawn contour on a rotated wing) with a 5 mm tolerance, so no wall end counted as 'on the face' and the side chain missed them (22 points on that side alone). Rule: (a) the face for the wall-run dimension points is the DRAWN face (extent of the contours of the walls and curtain bands drawn on that plan), the same quantity the reader's envelope is; (b) FACE_PT_TOL 5 mm -> 10 mm = the reader's `grid` tolerance (`EXT_FACE_TOL`/tolG), so writer and reader agree on 'on the face'. (c) the dimension strings run between the DRAWN extents (not the model box); (d) a piece touching the face counts with its whole extent along it (the reader reads a piece as its bounding rectangle: a chamfered wall end otherwise left its end unmeasured). Result: Hospital wing `dim_point_missing` 65 -> 13, blocking 470 -> 414; HHS 383 -> 379; Duplex marks and sheets identical. Left: 13 points on Levels 3-6, ends of 7 mm tessellation-sliver pieces (e.g. a 0.1 m x 7 mm wall piece at the building edge) that the reader measures and the writer does not. **Debt (stated):** the Python oracle `std2d.py` (BIMCompiler) does not have D10 (nor the JS-only marks rules D4-D8); parity on Duplex still holds because Duplex output is unchanged, but on HHS/Hospital the oracle differs: port D10 to the oracle before claiming parity there.

## 0. Verdict of 2026-10-19 (what is solid, what is not; measured, not felt)
**Solid (keep, build on):** deterministic pure modules (same sheets + markings = same model, byte for byte); settings travel INSIDE the DXF (`DXF2BIM-MARK` layer, plain text); yellow = a visible, listed setting with its basis (43 registry rows, no silent default); per-element evidence (sheet, handle, layer, size basis) into IFC and the DB; CLI and page give the same model (parity witnesses W-L29/W-L30); witnesses that name their issue and carry controls; a real answer-key proof (Duplex within 1 mm) and a write-back proof where no answer key exists (shed within 0.02 mm); the whole chain in a browser tab, MIT. The landscape rewards exactly this (trust, auditability, deterministic-first, openBIM mandates, SME cost barrier; see §7).
**Not yet solid (the work of this lane):**
1. **The emitted IFC is not conformant.** Independent check (IfcOpenShell 0.8.4 `validate`, schema level, on the shed IFC from BOTH writers): 23 errors. 20 = every `IfcDoor` is written with `*` (the derived-attribute marker) for OverallHeight, OverallWidth, PredefinedType, OperationType, UserDefinedOperationType (`#3274=IfcDoor('..',$,'Door ..',$,'Door ..',$,#3273,$,*,*,*,*,*)`); 3 = the STEP header FILE_NAME has no author / organisation. EXPRESS WHERE-rules were NOT run (the validator needs `pytest`, absent here). Also: no `IfcClassificationReference`, a single storey, no `IfcOwnerHistory` (optional in IFC4).
2. **The evidence property set is named `Pset_Dxf2Bim`.** The `Pset_` prefix is reserved for buildingSMART-defined sets; the buildingSMART validation service flags a `Pset_` set that is not one of theirs ([forum](https://forums.buildingsmart.org/t/are-there-rules-for-custom-pset-naming-conventions/4984), IFC4.4 IfcPropertySet page). It must be renamed (decision D1) with a read-compatible transition for existing DBs.
3. **No format contract.** The marks vocabulary, the CLI outputs (`bodies.json`, `ops.json`, `verdict.json`, `bill.json`), the DB tables (`element_dxf2bim`) and the error-code families (`GAP:*`, `QF:*`, `MARK:*`) are implicit in code. No version stamp, no schema, no compatibility rule.
4. **Generalisation is unproven.** One real whole-building 2D set with no 3D reference (the shed) + the Duplex (answer key) + a farmhouse set (read, not completed). The schedule reader's tolerances are absolute drawing units validated on ONE sheet (§L30); rules such as "single schedule row" are inferences that are stated in the data but untested elsewhere.
5. **CI does not exercise any of it.** The real-sheet witnesses SKIP in CI (private sheets); ten older witnesses cannot run on this machine (missing generated inputs under `~/Projects/bim-compiler/tests/dxf2bim/out/`; they fail identically before the §L29 changes). Green CI says nothing about the shed.
6. **No compliance output.** The library DB already holds a code layer (see §5) but nothing connects it to a DXF2BIM model, and no IDS file exists.

## 3. F3 Intake and benchmark harness for the new whole-building sets (the owner is getting more)
Spec: one repeatable procedure so each new set adds evidence instead of drift. (a) **Intake** `tools/dxf2bim_intake.js <set dir>` (read-only): sheets found, units (file header), entity counts by type and layer, blocks/xrefs/3D entities, text language, title-block presence, DWG-or-DXF; writes `intake.json` PRIVATE under `~/Projects/SYSNOVA/DXF2BIM/<set>/` and a de-identified summary row. Only reader gaps and builder gaps with drawn evidence become work; limits become documented yellow rows (the shed rule: do not build what the drawing does not carry). (c) **Metrics per set** (JSON, appended to a PRIVATE ledger; an aggregate table without client names goes to the public docs): time to first usable model (machine and typing), bodies per class, % of bodies derived/assumed, count of yellow rows and of facts stated, left-out count by code, IFC validation errors (F1), IDS pass rate (F4), round-trip write-back error where a plan is present, bill total. No target numbers until THREE sets are in: record first, then set. (d) **Regression:** every set that completes becomes a local witness with SKIP-loudly when its private sheets are absent, so the ten-witness gap of §0.5 does not grow; an `ALLWITNESS` runner prints PASS/FAIL/SKIP per witness and exits non-zero on any FAIL and on any unexpected SKIP list change. ## 3b. F3a Mixed sets (the first wall the new whole-building sets will hit; do it BEFORE running them blind)

## 3c. F3b Generality audit and guardrails (the owner asked: is the design truly general, or are we cheating ourselves as sets arrive?)
**Measured 2026-10-19 (engine = `modeller/dxf2*.js`, 3.4 k lines; searched for set-specific literals):**
- **Genuinely general (keep):** ZERO layer-name or sheet-name literals in any engine module (layers come only from the person's typing; the grep for `Rod|Win|Fo|Col|Dim|Tex|Wall` string literals returns nothing); the kinds table (11 body kinds -> IFC class) is data in one place; the defaults registry (43 keys), the evidence model, the marks-in-DXF format, determinism, the CLI/page parity are all set-independent. The same engine produced the Duplex (wall path) and the shed (body path).
- **General only at the typed-layer level, not at the convention level:** the SEMANTIC readers each encode a drawing convention validated by ONE set: panels = hatch loops on elevations; nets = hatch pattern name `zigzag|mesh|net|wire`; doors = plan swing symbols plus elevation frames; trusses = one section repeated at an assumed spacing; fans = circles in elevations; details = `f'c`, `fy`, `casting ratio`, `<KIND> SCHEDULE` in ENGLISH with feet-inch lengths. A set drawn in another office's convention or in Malay/Thai/Chinese will not match. That is expected for a start; it is a coverage matrix to be MEASURED, not assumed (F3 records which convention each set uses and which reader handled it).
- **Silent reader thresholds (the real self-deception risk):** 171 inline numeric comparisons against constants other than 0 and 1 across the 21 engine files (counted by W-GUARD; my first count of 'about 80' used a narrower pattern and was too low) (door overlap >= 0.8, leader distance 1 m, 1 mm alignment, 0.01 snap, 50% overlap, 5-unit row chaining, 6-unit header match...) against 43 registry rows of which the engine modules use about ten (`DF.use` count: doors 2, section 1, panels 3, synth 4, bodies 0). The yellow list is honest about DESIGN values; it is silent about READER heuristics. A set that works only because a threshold happens to fit would look like a success. Fix: a reader-tolerances registry (scale-relative, in the same registry or a sibling), each use recorded in `verdict.json` ("door overlap 0.8: matched 4 of 4, the nearest rejected was 0.62"), so a near-miss is visible.
- **Domain knowledge living in code:** `dxf2typology.js` (tunnel fans, evaporative pads) is a farming-shed advisory in logic; it belongs in a building-type pack (data). Every new building type would otherwise be code.
- **Effort does not yet scale:** the shed needed 10 layer typings, 5 datums (their y coordinates read by hand), 2 height ranges, 1 exclusion. The suggestion engine proposes only units, view/name, grid and datum; the layer meaning is always typed. Whole buildings with many more sheets multiply that. The ledger's "time to first usable model, expert and non-expert" will say whether this is acceptable; the library flywheel (F5.5) is the route to fewer typed facts.
- **The accuracy claim is narrower than it sounds:** the shed's 0.02 mm is SELF-consistency (the model written back to 2D matches the sheets it came from), not truth; only the Duplex has a 3D answer key and only on the wall path. The body path has no truth check. A truth proxy exists inside the drawings: the dimension audit (every typed dimension against its measured length) and the schedules' own sizes; make "dimension agreement rate" a recorded metric per set. Do not quote the 0.02 mm as accuracy.
**Guardrails (each a witness or a rule):** G1 **no-literals lint**: a witness fails if any engine module contains a layer name, sheet name, building name or client word as a string literal (today: zero; keep it zero). G2 **no per-set constants**: a fix for a set may add a typed fact, a registry row, a convention reader or a tolerance rule; it may never add a literal that names the set. G3 **tolerances in the registry** as above. G4 **blind first**: record failures before fixing (F3b protocol). G5 **a failing set stays in the ledger** with its failure class: the ledger is the honest record, not a showcase. G6 **claims discipline**: docs and films say "self-consistent within X" for body-path sets and "within X of an answer key" only where a 3D reference exists.

## 4. F4 Standards and compliance foundation
Spec: separate THREE things that are easy to mix up. (1) **Information requirements = IDS.** Write buildingSMART IDS 1.0 files for what the product promises: every element has the evidence set with Provenance and SourceSheet; allowed IFC classes and PredefinedTypes; project/site/building/storey present; materials named. Validate the product's IFC with `ifctester` (IfcOpenShell) in a witness; note the community complaint that one IDS gives different results in different tools ([IDS survey](https://www.buildingsmart.org/ids-survey-results-2026/)): record the tool + version with every result. (2) **Code compliance = rule packs, advisory only.** The library DB already has a data layer: `ad_building_code` (14), `ad_jurisdiction_codes` (17), `ad_code_requirement` (23), `ad_check_threshold`, `ad_check_applicability`, `ad_egress_travel`, `ad_stair_requirement` (IBC 2021, NEC 2020, IPC 2021, and Malaysian UBBL / MS 1184 / MS 1228 / MS IEC 60364 rows). Spec: export these as a versioned, cited, jurisdiction-scoped pack; AUDIT every row against the primary clause text (a row without a verified clause is marked `unverified` and never produces a finding; nothing is filled in from memory); first pack = Malaysia (UBBL fire / means of escape, MS 1184 accessibility) because the rows exist and the users are there. A finding states: clause, threshold, the measured value, the element ids, AND the evidence tier of the geometry it rests on (drawn / derived / assumed): a finding resting on assumed geometry is flagged low-confidence. That evidence-aware finding is what no AI tool in the landscape offers; keep it the point. Never word a finding as a legal determination. (3) **Classification** (decision D3): one scheme referenced in IFC (`IfcClassificationReference`) and in the library catalogue.

## 5. F5 One unified mesh store (the library and the Modeller's mesh.db are ONE thing, indexed once)
**Owner direction (2026-10-19):** reuse in a single place with an index, not split copies; unify the Modeller's `mesh.db` at OCI too; keep the client thin; the user chooses what to download.
**What exists today (measured read-only 2026-10-19; nothing was changed).** (a) `~/bim-compiler/library/component_library.db`: 230,539,264 bytes (2026-08-27, md5 c08b3dd0...), 23,888 definitions (23,884 distinct `geometry_hash`), 35 types, 4 source buildings (an IFC4 sample house, the IFC2x3 Duplex, a Malaysian low-cost house, an airport terminal), 51,088 of its 67,332 placements from ONE building; `component_geometries` is 195 MB of the 230. 16,010 definitions (67%) are mesh-per-size of three kinds (IfcPlate 8,022, IfcPipeFitting 4,200, IfcPipeSegment 3,788); one fitting name recurs 1,882 times with different geometry. The curated part is small: 68 opening families, 18 wall types, 5 column, 6 beam, 11 railing, 24 floor types, 9 building templates, 41 space types, 60 material layers, 80 surface styles. It also holds the code layer of §4. (b) The Modeller's `mesh.db`: a 120 MB shared store (`component_geometries`: `geometry_hash` PK, vertices, faces, building), Git-LFS-tracked, which GitHub Pages cannot serve (the live page got a 134-byte LFS pointer with HTTP 200, so every element silently fell back to its bounding box); on 2026-07-30 it was split into one `<Building>_geo.db` per resident, served from OCI (`bim-ootb/modeller/`, 8 files, 123.5 MB: Terminal 55.0, Hospital 49.6, SampleCastle 5.3, HHS 4.2, Clinic 4.1, HospitalGarage 2.4, Duplex 1.5, SampleHouse 1.4 MB). The Viewer has its own copies: `bim-ootb/buildings/` holds 88 objects, 1,381 MB, of which three `*_geo.db` are 217 MB (LTU_AHouse 95.7, Terminal 66.0, Hospital 55.4). Terminal and Hospital geometry are therefore stored at least twice (modeller/ and buildings/ differ in size, 55.0 vs 66.0 and 49.6 vs 55.4 MB: NOT yet hash-compared). (c) OCI `dxf2bim/library/7e5df6e10027/`: 191 objects, 1.5 MB (`latest.json` -> `index.json`, shards by `geometry_hash[0:2]`): 68 opening families, 18 wall types, 337 geometry-map rows, 331 meshes (doors and windows), made by `scripts/export_library_subset.js --full`: a third, independent copy format of the same hash space. (d) OCI root `component_library.db`: 477,155,328 bytes, modified 2026-04-20: not the local file (older, different size); unreconciled.
**Diagnosis.** One idea (a mesh is identified by its hash; a type or a building REFERENCES meshes) is implemented four times with four formats and no shared index. The split into `_geo.db` fixed a real delivery bug (LFS on Pages) by copying instead of referencing.
**Target: ONE logical store, ONE index, many views.** Tables: `mesh(hash PK, encoding, vertices, faces, normals, bbox, nverts, nfaces, bytes)`; `entry(id, ifc_class, predefined_type, name, family, params, classification, building_type, jurisdiction, provenance{source, licence, date})` (the curated catalogue: opening families, wall types, sections, railings, floors, coverings, fans, nets, door sets); `entry_mesh(entry, hash, role, lod)`; `tag(entry, facet, value)` for facets ifc_class x discipline x building_type x jurisdiction x lod x pack; `building_mesh(building, hash, count)` so a building REFERENCES shared meshes instead of owning a copy (what `_geo.db` becomes: a view/selection, not a file of bytes); standards tables of §4 in the same manifest (`standard_*`, small). Layers L0-L3 of the earlier draft are TAGS and tables of this one store, not separate files. Parametric families (plates, pipe and duct fittings and segments, sections) are stored as `parametric(profile, params)` entries that regenerate their meshes; only geometry that cannot be generated (doors, windows, fixtures, equipment) stays as stored mesh.
**Thin client, user choice (delivery, plain `fetch`, NO SharedArrayBuffer):** (1) the small index (catalogue + tags + hash -> shard map; 20 KB-200 KB, as `dxf2bim-library-index/1` is today) is always loaded; (2) meshes are fetched on demand by hash from content-addressed shards (by hash prefix, as now) or by HTTP Range from one packed file with an offset table (OCI supports Range; the app is hosted on GitHub Pages, which only has to serve the app); (3) **packs** = named selections by tag (e.g. `starter` doors/windows/wall types about 1.5 MB, `structure`, `mep`, `terminal`, `all`) that the user may download once into IndexedDB/OPFS, versioned by manifest sha, every fetched byte hash-verified; (4) the full `mesh-all-<sha>.db` SQLite is a BUILT export of the same store for offline/dev use, never hand-maintained. Do NOT re-attempt sqlite-over-HTTP range VFS from GitHub Pages (needs SharedArrayBuffer/COOP-COEP, which Pages cannot send; recorded in the memory of 2026-06). Never commit library or mesh data to git/LFS.
**Work (in order):** (1) `tools/library_audit.js` + `tools/mesh_overlap.js` (read-only, reproducible): the §5 numbers per facet AND the hash overlap between component_library.db, the OCI `_geo.db` files (download them once into a scratch dir), the `dxf2bim/library` shards and the Duplex/Terminal/Hospital buildings: how much is duplicated, how much is unique; this decides the size of the unified store (do not promise a number before it is measured); (2) manifest `dxf2bim-library/2` (above tables; readable by v1 loaders; provenance + licence + classification + tags per entry); (3) classify the 23,888 definitions: promote to the catalogue, collapse into parametric families (verify by regenerating the collapsed meshes within a stated tolerance and LIST what does not collapse), keep as stored mesh, archive, drop exact duplicates; (4) the loader in the Modeller and the Viewer reads by hash from the one store (feature-flagged, `_geo.db` still honoured until parity is witnessed per building); (5) **the flywheel:** every whole-building set that completes contributes the types it DREW (fans, nets, door sets, sections) to the catalogue with provenance "drawn", de-identified, so a Farming Shed (no component exists today) and every later building type get a cited library without inventing anything; (6) publish new versioned prefixes under `bim-ootb/dxf2bim/` (or a successor prefix) ONLY on the owner's go; leave the OCI root `component_library.db` and the existing `modeller/` and `buildings/` objects untouched and documented as legacy until each building passes parity; reconcile the root file with the local one only with the owner (D4). Witnesses: **W-STORE-AUDIT** (numbers reproducible; fails on an entry with no provenance or a mesh with no hash match), **W-STORE-PARITY** (per building, the meshes resolved through the unified store are byte-identical to its `_geo.db`: this is the safety net for the migration), **W-STORE-HASH** (every shard/pack hash matches its index), **W-STORE-PARAM** (a parametric family regenerates what it replaces within tolerance), **W-STORE-NOLEAK** (no client or sponsor name in any published manifest, shard or entry name; names such as source-prefixed fittings must be checked first), **W-STORE-THIN** (a cold client opening the Duplex fetches only the index plus the meshes the Duplex uses: record the bytes; no regression against the 1.2 MB of §GEO-SERVED).

## §D53 BEST-EFFORT MATERIALS: THE REFERENCE BY CLASS, A FIRM'S CATALOGUE BY THICKNESS (architect review F6 / R4.4; owner 2026-10-23: best-effort defaults, editable in JSON)

`e.ifc.material` (IfcMaterial + IfcRelAssociatesMaterial); the Viewer db then carries `material_name` for the BOM and the material lens. The catalogue is a file the user keeps or edits;
`catalogue_from_ifc.js` writes it from the firm's own IFC (counts only, nothing invented).
