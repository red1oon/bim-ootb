## 0. Verdict of 2026-10-19 (what is solid, what is not; measured, not felt)
**Solid (keep, build on):** deterministic pure modules (same sheets + markings = same model, byte for byte); settings travel INSIDE the DXF (`DXF2BIM-MARK` layer, plain text); yellow = a visible, listed setting with its basis (43 registry rows, no silent default); per-element evidence (sheet, handle, layer, size basis) into IFC and the DB; CLI and page give the same model (parity witnesses W-L29/W-L30); witnesses that name their issue and carry controls; a real answer-key proof (Duplex within 1 mm) and a write-back proof where no answer key exists (shed within 0.02 mm); the whole chain in a browser tab, MIT. The landscape rewards exactly this (trust, auditability, deterministic-first, openBIM mandates, SME cost barrier; see §7).
**Not yet solid (the work of this lane):**
1. **The emitted IFC is not conformant.** Independent check (IfcOpenShell 0.8.4 `validate`, schema level, on the shed IFC from BOTH writers): 23 errors. 20 = every `IfcDoor` is written with `*` (the derived-attribute marker) for OverallHeight, OverallWidth, PredefinedType, OperationType, UserDefinedOperationType (`#3274=IfcDoor('..',$,'Door ..',$,'Door ..',$,#3273,$,*,*,*,*,*)`); 3 = the STEP header FILE_NAME has no author / organisation. EXPRESS WHERE-rules were NOT run (the validator needs `pytest`, absent here). Also: no `IfcClassificationReference`, a single storey, no `IfcOwnerHistory` (optional in IFC4).
2. **The evidence property set is named `Pset_Dxf2Bim`.** The `Pset_` prefix is reserved for buildingSMART-defined sets; the buildingSMART validation service flags a `Pset_` set that is not one of theirs ([forum](https://forums.buildingsmart.org/t/are-there-rules-for-custom-pset-naming-conventions/4984), IFC4.4 IfcPropertySet page). It must be renamed (decision D1) with a read-compatible transition for existing DBs.
3. **No format contract.** The marks vocabulary, the CLI outputs (`bodies.json`, `ops.json`, `verdict.json`, `bill.json`), the DB tables (`element_dxf2bim`) and the error-code families (`GAP:*`, `QF:*`, `MARK:*`) are implicit in code. No version stamp, no schema, no compatibility rule.
4. **Generalisation is unproven.** One real whole-building 2D set with no 3D reference (the shed) + the Duplex (answer key) + a farmhouse set (read, not completed). The schedule reader's tolerances are absolute drawing units validated on ONE sheet (§L30); rules such as "single schedule row" are inferences that are stated in the data but untested elsewhere.
5. **CI does not exercise any of it.** The real-sheet witnesses SKIP in CI (private sheets); ten older witnesses cannot run on this machine (missing generated inputs under `~/Projects/bim-compiler/tests/dxf2bim/out/`; they fail identically before the §L29 changes). Green CI says nothing about the shed.
6. **No compliance output.** The library DB already holds a code layer (see §5) but nothing connects it to a DXF2BIM model, and no IDS file exists.

## 1. F1 IFC conformance gate (do FIRST; small, high leverage)
Spec: every IFC the product writes (headless `modeller/dxf2ifc.js` AND the page `modeller/bonsai_ifc.js`) passes `ifcopenshell.validate` (schema level) with ZERO errors, and, once `pytest` is installed in the dev environment (owner's call, local dev tool), with the EXPRESS rules too. Work: (a) doors: write OverallHeight/OverallWidth from the body's own size, PredefinedType DOOR, OperationType NOTDEFINED unless a swing is drawn (a drawn swing may set SINGLE_SWING_LEFT/RIGHT only from drawn evidence); (b) header FILE_NAME author/organisation as the empty list, file description, schema `IFC4`; (c) rename the evidence pset (D1) in both writers, the extractor (`BIMCompiler scripts/ifc_extract_core.js`, BIMCompiler change first, then `modeller/dxf2bim/sync.sh`), the Viewer panel (`viewer/info_dxf2bim.js` reads the table, not the pset, so it only needs the DB), the docs; the extractor reads BOTH names so old DBs keep working; (d) use standard psets where one exists instead of a custom key: verify the exact IFC4 names against the buildingSMART documentation before using them (e.g. `Pset_MaterialConcrete` / `Pset_MaterialSteel` for the concrete and steel grade, `Qto_*BaseQuantities` for areas and volumes the product already measures); keep a custom namespaced set only for evidence; (e) a classification reference (decision D3). Witness **W-IFC-VALID** (python, SKIP loudly without ifcopenshell, never silently): the shed IFC from the CLI and from the page, the Duplex IFC, and a control that deliberately reintroduces the `*` door (must FAIL). Issue it names: "the file is valid IFC", not "the file opens in our viewer". Also run the buildingSMART online validation service by hand once and keep its report in `docs/` (no private data).

## 2. F2 Format contract
Spec: (a) a version stamp in the settings sheet (`@FORMAT=dxf2bim-marks/1`, absent = version 1 read as today) and in every CLI JSON (`format` field); (b) `docs/DXF2BIM_FORMAT.md` generated from the code's own tables (marks vocabulary from `dxf2marks.js`, defaults from `element_defaults.json`, error codes by grep of `GAP:|QF:|MARK:`), with JSON Schemas for `bodies.json`, `ops.json`, `verdict.json`, `bill.json`; a witness validates real outputs against the schemas; (c) the compatibility rule written down: a reader accepts every older version; a writer states the version; removing or renaming a key needs a version bump and a migration note; (d) the `element_dxf2bim` table gets a `format` row/meta table. Do NOT redesign anything: freeze and document what exists. Issue it names: "another tool or another session can read our files without reading our code".

## 3. F3 Intake and benchmark harness for the new whole-building sets (the owner is getting more)
Spec: one repeatable procedure so each new set adds evidence instead of drift. (a) **Intake** `tools/dxf2bim_intake.js <set dir>` (read-only): sheets found, units (file header), entity counts by type and layer, blocks/xrefs/3D entities, text language, title-block presence, DWG-or-DXF; writes `intake.json` PRIVATE under `~/Projects/SYSNOVA/DXF2BIM/<set>/` and a de-identified summary row. (b) **Blind protocol:** freeze the code at a commit, run the suggestions (Accept all) + the CLI with only the facts a person can state, and RECORD every failure BEFORE touching code; classify each failure: reader gap (layer semantics, units, hatches, blocks, polylines, DWG conversion), missing fact (should be a yellow row), builder gap (element the product does not build and the drawing carries), or true limit (the drawing does not state it). Only reader gaps and builder gaps with drawn evidence become work; limits become documented yellow rows (the shed rule: do not build what the drawing does not carry). (c) **Metrics per set** (JSON, appended to a PRIVATE ledger; an aggregate table without client names goes to the public docs): time to first usable model (machine and typing), bodies per class, % of bodies derived/assumed, count of yellow rows and of facts stated, left-out count by code, IFC validation errors (F1), IDS pass rate (F4), round-trip write-back error where a plan is present, bill total. No target numbers until THREE sets are in: record first, then set. (d) **Regression:** every set that completes becomes a local witness with SKIP-loudly when its private sheets are absent, so the ten-witness gap of §0.5 does not grow; an `ALLWITNESS` runner prints PASS/FAIL/SKIP per witness and exits non-zero on any FAIL and on any unexpected SKIP list change. (e) Generic code only: no per-building constants (the §L30 tolerances must become relative to the sheet's own scale, e.g. derived from the header cell height, before a second details sheet is read; make that its first F3 task and add a witness that scales the real details sheet 10x and expects the same table).

## 4. F4 Standards and compliance foundation
Spec: separate THREE things that are easy to mix up. (1) **Information requirements = IDS.** Write buildingSMART IDS 1.0 files for what the product promises: every element has the evidence set with Provenance and SourceSheet; allowed IFC classes and PredefinedTypes; project/site/building/storey present; materials named. Validate the product's IFC with `ifctester` (IfcOpenShell) in a witness; note the community complaint that one IDS gives different results in different tools ([IDS survey](https://www.buildingsmart.org/ids-survey-results-2026/)): record the tool + version with every result. (2) **Code compliance = rule packs, advisory only.** The library DB already has a data layer: `ad_building_code` (14), `ad_jurisdiction_codes` (17), `ad_code_requirement` (23), `ad_check_threshold`, `ad_check_applicability`, `ad_egress_travel`, `ad_stair_requirement` (IBC 2021, NEC 2020, IPC 2021, and Malaysian UBBL / MS 1184 / MS 1228 / MS IEC 60364 rows). Spec: export these as a versioned, cited, jurisdiction-scoped pack; AUDIT every row against the primary clause text (a row without a verified clause is marked `unverified` and never produces a finding; nothing is filled in from memory); first pack = Malaysia (UBBL fire / means of escape, MS 1184 accessibility) because the rows exist and the users are there. A finding states: clause, threshold, the measured value, the element ids, AND the evidence tier of the geometry it rests on (drawn / derived / assumed): a finding resting on assumed geometry is flagged low-confidence. That evidence-aware finding is what no AI tool in the landscape offers; keep it the point. Never word a finding as a legal determination. (3) **Classification** (decision D3): one scheme referenced in IFC (`IfcClassificationReference`) and in the library catalogue.

## 5. F5 Library organisation (measured 2026-10-19, read-only; nothing was changed)
**What exists.** (a) Local `~/bim-compiler/library/component_library.db`: 230,539,264 bytes (2026-08-27, md5 c08b3dd0...): 23,888 definitions / geometries (23,884 distinct hashes), 35 types, 67,332 placements of which 51,088 belong to ONE source building; the registry names 4 source buildings (an IFC4 sample house, the IFC2x3 Duplex, a Malaysian low-cost house, an airport terminal); `component_geometries` is 195 MB of the 230. Two thirds of the definitions are mesh-per-size of three kinds: IfcPlate 8,022, IfcPipeFitting 4,200, IfcPipeSegment 3,788 (16,010 = 67%); the same NAME recurs with different geometry (one transition fitting 1,882 times); names carry the source's prefix. The curated part is small: 68 opening families, 18 wall types, 5 column types, 6 beam types, 11 railing types, 24 floor types, 9 building templates, 41 space types, 60 material layers, 80 surface styles. (b) OCI `bim-ootb/dxf2bim/library/7e5df6e10027/` (191 objects, 1.5 MB, `latest.json` -> `index.json`, shards by `geometry_hash[0:2]`): the DXF2BIM subset only: 68 opening families + 18 wall types + 337 geometry-map rows + 331 meshes (doors and windows), generated by `scripts/export_library_subset.js --full`. (c) OCI root `bim-ootb/component_library.db`: 477,155,328 bytes, last modified 2026-04-20: NOT the same file as the local one (older, different size); unreconciled. Also `dxf2bim/samples/duplex` (17 objects, 1.4 MB).
**Diagnosis.** There is no library to organise yet; there are three things under one name: a harvest of four extracted buildings (compiler input), a small curated catalogue (what DXF2BIM actually uses, 0.65% of the DB by size), and a code layer. They have different lifecycles, licences and audiences.
**Target layout (by purpose and lifecycle, all content-addressed and versioned; shards stay small and lazy):**
- **L0 standards pack**: jurisdiction -> code -> clause -> threshold (§4), cited, `verified|unverified` per row.
- **L1 type catalogue**: parametric families (opening families, wall types, column/beam/footing sections, railings, floors, coverings, fans, nets, door sets) keyed by IFC class + PredefinedType + classification code + building-type tags (§L23) + jurisdiction; defaults and ranges; per-entry provenance {source building or "drawn set <de-identified id>", licence, date}.
- **L2 geometry store**: meshes by hash, each entry either `mesh` (doors, windows, fixtures, equipment: geometry not generable) or `parametric(profile, params)` (plates, pipe and duct fittings and segments, sections: regenerate, do not store one mesh per size).
- **L3 harvest archive**: the 23.9K-mesh dump, kept as the compiler's source archive with its per-building provenance; not shipped to DXF2BIM; names neutralised before anything from it is published.
**Work (in order):** (1) `tools/library_audit.js` (read-only, reproducible): the numbers above per facet (class x discipline x source building x tier), written as `library_audit.json` + a generated docs page "Library map"; (2) manifest `dxf2bim-library/2` adding provenance, licence, classification, tags to every entry, still readable by v1 loaders; (3) classify the 23,888 definitions: promote to L1, collapse into parametric families (verify equivalence by regenerating the collapsed meshes within a stated tolerance; list what does not collapse), archive, drop exact duplicates; (4) **the flywheel**: every whole-building set that completes contributes the types it DREW (fans, nets, door sets, sections) to L1 with provenance "drawn", de-identified; this is how a Farming Shed (no component exists today) and every later building type get a cited library without inventing anything; (5) publish L0/L1/L2 as new versioned prefixes under `bim-ootb/dxf2bim/` ONLY on the owner's go; leave the OCI root `component_library.db` untouched and documented as legacy; reconcile it with the local file only with the owner (decision D4). Witnesses: **W-LIB-AUDIT** (numbers reproducible; fails on a definition with no type or no provenance), **W-LIB-HASH** (every shard hash matches its index), **W-LIB-PARAM** (a parametric family regenerates the meshes it replaces within tolerance), **W-LIB-NOLEAK** (no client or sponsor name in any published manifest or shard name; today's names such as source-prefixed fittings must be checked first).

## 7. Evidence base for the strategy (searched 2026-10-19; thin and mostly vendor or anecdotal, no independent accuracy benchmark was found: say so wherever it is quoted)
Pain list (forums): DWG imports look flat and non-native; exploding or tracing leaves broken lines and off-axis warnings; clients must state exactly what they want; infrastructure users ask for a library of converted standard details; clean-up overhead and lost design intent dominate ([Revit forum](https://www.revitforum.org/forum/revit-architecture-forum-rac/architecture-and-general-revit-questions/30953-revit-dwg-import-frustrations/page5), [Autodesk forum](https://forums.autodesk.com/t5/autocad-lt-forum/converting-autocad-dwg-to-revit-rvt/td-p/4962608), [vendor guide](https://designdrafter.com/cad-to-revit-conversion-the-complete-guide-to-bim-automation/)). AI tools: walls, doors, windows, slabs only; practitioners report over 80% of walls caught, door swings misread, clean plans required ([roundup](https://dancumberlandlabs.com/blog/revit-construction/)); round trips map beams, stairs and roofs to generic masses ([review](https://archigenai.com/snaptrude-ai-bim-review-architects-2026.html)). Literature: benchmarks are raster residential floor-plan images scored by IoU/F1 (CubiCasa5k, [arXiv 2306.01642](https://arxiv.org/abs/2306.01642)); no standard 3D-level metric (height, volume), no survey. Industry: openBIM mandates name IFC, IDS, BCF ([bSI 2025](https://www.buildingsmart.org/wp-content/uploads/2025/03/IFC-Mandate_2025.pdf)); IDS users value automated checking, complain of tool-to-tool differences, 74% want LOIN alignment; IFCX (IFC5) core plan approved August 2026, alpha only ([bSI](https://www.buildingsmart.org/ifcx-core-modularisation-project-update/)); AI-in-BIM reviews ask for human review, explainability, data lineage and audit trails ([MDPI](https://www.mdpi.com/2076-3417/15/18/9956)); a Canadian call asks for a DETERMINISTIC human-in-the-loop compliance checker ([ISED](https://ised-isde.canada.ca/site/innovative-solutions-canada/en/deterministic-artificial-intelligence-assisted-compliance-checking-building-permit-applications)). Long tail: cost is the first barrier for Malaysian SME contractors (software, hardware, training, certification; CIDB ranking 26.2%), uptake still below expectation ([review](https://www.researchgate.net/publication/383510217_Review_of_Building_Information_Modeling_BIM_Adoption_Amongst_SMEs_in_the_Malaysian_Construction_Industry)); open-source Bonsai users ask for better DXF import/export and hand-roll DWG -> DXF -> IFC for takeoff ([OSArch](https://community.osarch.org/discussion/2737/what-does-bonsai-need-to-be-ready-for-a-basic-architectural-drawing-pack)); paid modelling from 2D is quoted at roughly $0.30-$2.00 per square foot, level of detail being the driver ([vendor](https://www.thefuture3d.com/learn/bim-cost-per-square-foot/)).
**Reading of the pond.** The crowded pond is AI-generated walls for architects. Ours is evidence-first, standards-conformant conversion of engineering sets for people who cannot pay the services price: smaller, underserved, and aligned with the trust and mandate signals. The measures practitioners actually use (share of elements fixed by hand, time to first usable model, silent defaults, round-trip error, validation and IDS pass) are the ones F3 records; nobody publishes them for this task, so publishing them is itself the credibility. Risk to watch: the casual user wants one click, and typing layer meanings is expert work; F3's blind runs must also record the time a NON-expert needs, and the library flywheel (F5.4) is the route to fewer typed facts.
