## §1 Issue (measured)
- **Precision:** the Modeller IFC open route keeps raw map coordinates; the Viewer import shifts to a local origin. At map coordinates (x ≈ 500 km, y ≈ 3,000 km class), world-scale float32 loses up to 1.6 cm in x and 12.5 cm in y. That float32 lives in the scene meshes and the export (`modeller/bonsai_library.js:87,100` `place()` → `bonsai_ifc.js` `triFaceSet`).
- **Proof:** W-EXPORT-ROUNDTRIP far leg, PR #2708. `§RT-PRECISION float32 on x and y CONFIRMED`: max |dx| 0.0134 m against a half-step of 0.0156; max |dy| 0.1165 against 0.125. Local Duplex: all within 1 mm.
- **Effect on the private set:** 1,284 of 4,147 elements moved more than 1 cm through export.
- **Two frames:** the two routes give one file two frames, so a camera path or grid made on one route does not sit on the other.

## §2 Rule (A): open route, built first
1. **ONE implementation.** Lift the import's rebase rule (`viewer/import_worker.js` ~700-755: the per-axis > 10 km test, the whole-metre offset, the federation pin, the > 1 km disagreement fallback) into a shared module under `common/`. Both routes call it. The import's behaviour must not change (same offsets, byte-identical DB on the residents). No second copy in the open route.
2. **Shift EVERY world-coordinate column of the opened DB.** Columns are found by a sweep of the DB's tables and names (`center_*`, `x0/y0/x1/y1`, `minX..maxZ`, `door_operation` x/y/z, `ifc_spaces` centres, `ifc_grid_axis` ends, `element_world_bbox`; `storey_elevation` only if z shifts), not by a hand list. Element-local geometry blobs do not move.
3. **Record** `georef_offset_x/y/z` in `project_metadata`, exactly as the import does.
4. **Read the site facts, never invent them:**
   - IfcSite RefLatitude/RefLongitude (compound angles) → `site_latitude` / `site_longitude`;
   - true north from the geometric context's TrueNorth;
   - IfcMapConversion (IFC4) if present;
   - the source recorded as `site_latlong_source`, the way the import names it (restore it on the import too where it is empty today).
5. **Federation:** files opened together (e.g. ARC + STR) share one pin, as the import does.

### §2a ONE input for the pin (bug fix, 2026-11-08)
**Defect (measured by the design lane on a private Revit file, main fbe06d64):** the same file gave offsets 11 m apart in y on the two routes; the final element sets compared equal (2,093 transforms) because `ifc_open_db.js` drops IfcSpace/IfcOpeningElement rows later.
**Cause (code read):** both routes call `GF.range(transforms)` then `GF.pin(...)` (`ifc_extract_core.js` ~L611, `import_worker.js` ~L712), but `transforms` holds different elements at that moment:
- Open: `PRODUCT_TYPES` (`ifc_extract_core.js` L306-352) INCLUDES `IFCSPACE` and `IFCOPENINGELEMENT`; every one that tessellates pushes a transform (L536). Import's list (`import_worker.js` L378-412) excludes both ("IfcSpace + IfcSite excluded").
- Import additionally skips `_SKIP_GEOM` classes (IfcFireSuppressionTerminal, IfcAlarm, IfcSensor, IfcActuator, IfcController, IfcFlowInstrument, IfcProtectiveDeviceTrippingUnit; L493-494) before tessellation; Open tessellates them.
- Centre definition (vertex mean, world metres, before rebase) is the same in both (L496-498 / L558-560); autoScale in Open fires only for a >500 m spread (mm file) and Import's web-ifc already yields metres: not a difference here.
One far room volume or void therefore moves the min/max midpoint on Open only.
**Rule:** both routes pass the SAME rows to `range()`, defined in ONE place: `GeorefFrame.pinInput(transforms, classByGuid)` in `common/georef_frame.js` drops rows whose class is in `PIN_EXCLUDED_CLASSES` (the classes the import never produces: IfcSpace, IfcOpeningElement, IfcSite/Building/Storey/Annotation/Grid/VirtualElement, and the `_SKIP_GEOM` list). That IS the import's set, so import offsets on the residents do not move (W-ONE-FRAME F5 proves it). Only rows entering `range()` are filtered; `rebase` still shifts every row. No rows left => no pin (as the import with no transforms). The rule's meaning is unchanged: midpoint of element centres, >10 km, whole metres; no switch to the stated site placement.
**Witness:** W-ONE-FRAME F1d (far Duplex + one cloned IfcSpace / IfcOpeningElement 30 m off in y, `lib_far_fixture.js` `opts.outlier`): both routes identical; import equals the plain far copy; RED: origin/main gives different offsets on the same fixture.
