## Design
1. ONE layering utility `erp/layered_registry.js` (UMD): `create()` -> add(key, value, {owner, rank}), remove(key, owner), removeOwner(owner), top(key), layers(key), keys(). Effective entry = highest rank, then latest registration. Core registrations have owner 'core', rank 0; bundle registrations default rank 1 (Libero's own DS ranking is 1). Used by every registry below (AD-LAYER rule 5: one implementation).
2. model_layer: `registerModel(table, impl, opts)` keeps layers; MODEL[table] = per-hook merge in layer order (a higher layer overrides only the hooks it defines); `unregisterModel(table, owner)`; same for `registerDocAction`/`unregisterDocAction`. Calls with no opts behave exactly as today.
3. ad_modelval: `unregisterValidator(table, timing, name)`. ad_process: `registerHandler`/`defineProcess` layered + `unregisterHandler`/`undefineProcess(owner)`. ad_callout: `registerHandler`/`defineCallout` layered + removal by owner.
4. doc_poster: `registerDocClass(table, impl, opts)` / `unregisterDocClass(table, owner)`; `derivePostings` consults it before the final fallback (impl.derive(db, id, schema, R, recordRef) returns the same shape as the existing derive*); `immediatePostingRefusal` treats a table with a registered class as having a Doc class.
5. plugin_registry: every bundle gets SCOPED facades for modelval / callout / process / docAction / docClass / postTokens / dict; the scope records each contribution with its owner (= bundle id) and `stopBundle` undoes them all automatically (the bundle's own `deactivate` still runs first for anything custom). `ctx.dict.activate(table, idCol, ids)` flips IsActive to 'Y' through the writable db host, remembering previous values; undo restores them.
   Atomic start: if activate (or a hot chunk) throws, every contribution so far is undone, the state returns to INSTALLED and the error propagates. `manifest.chunks.hot` = relative module URLs loaded and activated in order BEFORE the state becomes ACTIVE; `manifest.budget` = {kb, note} is stored and listed (informational). `restore(records)` re-installs and restarts persisted ACTIVE bundles (what plugin_overlay _hydrate does by hand today).
6. Not in H1 (named): lazy chunks; the lifecycle for UI forms; per-role scoping of hot hooks (decision: live for everyone while ACTIVE).

## H2 - OSGi-style LAZY ACTIVATION (user, 2026-10-15: "in OSGi there is also lazy loading which the user chooses; I think they are made active when dependencies are detected, i.e. by a Sales Order")
Supersedes my H1 note "lazy chunks cannot serve processes": that was too absolute. Legacy evidence (pshepetko/org.idempiere.mfg, MANIFEST + OSGI-INF): `Bundle-ActivationPolicy: lazy`, `Bundle-Activator: org.adempiere.plugin.utils.Incremental2PackActivator` (applies the bundle's dictionary pack when it ACTIVATES), three DS components with NO `immediate`
attribute (delayed: the service entry is registered at start, the class is loaded on the first request); the server starts bundles by configured start level (laos config.ini `osgi.bundles.defaultStartLevel=4`, simpleconfigurator). So legacy has TWO steps the admin controls: START (listed/configured) and ACTIVATE (first demand by a consumer, e.g. the first model lookup that reaches the bundle's factory).
Our constraint is only that dynamic import is async while ModelLayer.run is sync. MEASURED: all model calls funnel through ONE async callback seam, `crud_overlay.modelRun(spec, cb)` (:1617, 3 call sites: BEFORE_SAVE :1654, DOCACTION :1953, AFTER_SAVE :2482), so activation can happen BEFORE `ML.run`.
Design: manifest `activation: 'eager'|'lazy'` (default eager) + `triggers: {tables:[], processes:[], windows:[]}`; an admin override per bundle (`setPolicy`, persisted). State STARTING (OSGi STARTING) = started, hooks NOT live, code not loaded; `need({table|process|window})` activates every STARTING bundle whose trigger matches (dependency order, one activation per bundle even under concurrent demand), records a signed `PLUGIN_ACTIVATE` op (replay knows when hooks came alive), and an activation failure is atomic. `stop` of a STARTING bundle just cancels it. `restore()` brings ACTIVE and STARTING bundles back as started under their policy.
Seam wiring: crud_overlay modelRun + fireBeforeSaveHooks call `PluginEngine.need({table})` first. NAMED residual risks: (1) a CASCADE inside one run (a doc action creating rows in a table whose hooks sit in a still-STARTING bundle): the registry/seam logs `§PLUGIN-LAZY-MISSED` (table, bundle) when a run touches a declared trigger table of a bundle that was not yet active, and activates it for the next run - visible, never silent; bundles whose correctness needs cascade tables should declare them as triggers of the entry tables or choose eager;
(2) callouts and window-open triggers are not wired to the grid yet (processes/windows declared but only `need` by table is called at the model seam); bundles with callouts stay eager until that seam is wired.
Witness additions to W-PLUGIN-LIFECYCLE: P9 lazy start = STARTING, activate NOT called, dump == baseline; P10 `need` on a trigger table activates (contributions live, PLUGIN_ACTIVATE logged); P11 `need` on another table does nothing; P12 concurrent `need` activates once; P13 stop in STARTING cancels, stop after activation == baseline; P14 admin policy override eager makes start immediate; P15 lazy activation failure is atomic and surfaces to the caller; P16 restore() brings a STARTING/ACTIVE bundle back as STARTING (lazy) and a later `need` activates it. Break: `MFG_BREAK=eagerlazy` (lazy bundle activated at start) -> P9 FAIL.

## H2b (2026-10-15, found building the Libero bundle): `manifest.dictionary` - the 2Pack part of a bundle
A lazy bundle triggered by a WINDOW is only reachable through its menu leaf, so the menu rows cannot wait for activation. `manifest.dictionary = [{ table, idCol, rows }]` is staged at START (lazy: while STARTING; eager: with the activation), refcounted by `ctx.dict.insert` semantics (a base row is never touched or deleted), and undone at STOP (STARTING or ACTIVE) or when an activation fails. `restore()` re-stages it at boot because it goes through `startBundle`. Witnesses: `witness_libero_bundle.js` L1/L7c/L7d, `poc_libero_live.js` V1. Grid triggers (window/process) landed earlier the same day (`poc_plugin_grid_triggers_live.js`).
