## Issue it proves or disproves
Can the Manufacturing layer be a bundle that (a) costs nothing and changes nothing while not active, (b) wakes on its first consumer (window 53009, a covered table, a Libero process), (c) when active makes `ModelLayer.save` of a `pp_order` write the same child rows the Java writes (`pp_order_bom`, `pp_order_bomline`, `pp_mrp`) through `Trx`, and (d) when stopped leaves the base byte-identical (dictionary, registries, data kept).

## DECISION RECORDED — source vs. the shipped seed rows (found 2026-10-15, measured, not assumed)
The seed's legacy orders 8000/8001 are **2008 GardenWorld demo data**, not output of the current Libero source. Three measured differences:
1. `PP_Order_BOMLine.QtyRequired`: seed `5050.50505051` (8 dp) but the line UOM (50001 kilogram) has StdPrecision 2; the source (`MPPOrderBOMLine.setQtyRequired` :330 and `beforeSave` :163-168) rounds to the UOM precision (HALF_UP, then UP) -> `5050.51` / `7070.71`; UOM 100 (Each, precision 0) -> `100`.
2. `PP_Order_BOM.BOMUse`: seed `M` (template `A`); the source constructor (`MPPOrderBOM(MPPProductBOM, ...)` :70-93) copies `setBOMUse(bom.getBOMUse())` -> `A`.
3. `PP_MRP` supply `DateFinishSchedule`: seed = order DateStartSchedule (08-16); source `MPPMRP.setPP_Order` copies `o.getDateFinishSchedule()` (08-17) (this resolves the "AMBIGUOUS" note of M5).
**Rule applied: the SOURCE is the oracle for behaviour; the seed rows are the oracle only for the fields where the 2008 rows and the source agree.** The witness prints each divergence as `§LIBERO-SEED-DELTA` with the computed source value and the seed value, so the delta is a measured fact, not a silent change. This supersedes the "102 fields, 0 diff" claim of M3 for the three items above; the M3/M4/M5 kernel-path witnesses are unchanged (they test the 5-table kernel path, a different substrate).
Reversible: if the owner states the seed behaviour must win (e.g. a Libero fork that really behaves like 2008), only the three constants in `libero_pporder.mjs` change.

## Witness `witness_libero_bundle.js`
Real sql.js, seed + patches, real `ModelLayer`/`PluginRegistry`. Cases (each names the issue):
- L0 BASELINE hash of {ad_menu, MODEL/validator registries, pp_* row counts}. L1 install+START lazy: STARTING, hash unchanged (no code ran).
- L2 DEMAND: `need({window:53009})` activates it; the 4 menu rows exist; `getMenuTree` reaches window 53009 (the M1 oracle, now through the bundle).
- L3 EXPLOSION: `ML.save(trx,'pp_order',...)` for the two legacy orders' inputs (product 136/50007, qty 100, BOM 50004/50005, start 2008-08-16): rows written are compared field by field to the legacy `pp_order_bom`/`pp_order_bomline` rows; every difference must be one of the three declared deltas (printed `§LIBERO-SEED-DELTA`), anything else FAILs. Non-vacuity: the compared field count is printed and must be >0.
- L4 MRP: demand rows (one per BOM line) + one supply row; all fields except minted ids/clock compared to the legacy `pp_mrp` rows with the declared delta (DateFinishSchedule). Re-saving the order without a relevant change adds no MRP row (`isChanged` false); changing QtyOrdered updates the supply in place (`getQuery(...).firstOnly()`).
- L5 EFFECTIVITY: order start before BOM ValidFrom -> save refused with the BOMExpired reason, NOTHING written; line with ValidTo before the start date is excluded (M4 semantics over real tables).
- L6 REFUSALS from `beforeSave`: Org 0 with no context org; BOM product != order product; unverified product.
- L7 STOP: hash == L0 hash (menu rows gone, registries restored), the data rows written in L3-L4 are KEPT; restart is idempotent (same hash as after the first start).
- L8 DEFERRALS visible: the witness prints `§LIBERO-DEFERRED` for orderStock, routing, phantom, reserveStock so none is silent.
- Deliberate breaks (`LIBERO_BREAK=<name>` must exit 1): `uom` (skip precision rounding), `bomuse` (force 'M'), `eager` (activate without demand -> L1 fails), `nostop` (leave registrations -> L7 fails), `mrpfinish` (supply finish from DateStartSchedule -> L4b fails).
